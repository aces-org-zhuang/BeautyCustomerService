# 知识变更到用户回答闭环 PRD

状态：目标需求，部分能力已实现。

## 背景

当前系统已经能把人工反馈或材料蒸馏结果写入 LLM Wiki，并能把通过审核与评估的知识同步到 RAGFlow。用户进一步提出：知识回写 LLM Wiki 之后，如果运营在 LLM Wiki 中继续新增、修改、删除或驳回内容，这些变化是否会同步 RAGFlow，并最终改变前端用户咨询结果。

本 PRD 定义这条完整闭环的产品要求。技术策略见 `../05-contracts/knowledge-change-to-answer-loop-strategy.md`。

## 问题定义

知识写入 LLM Wiki 只是治理链路的起点。若没有后续闭环，运营无法判断：

- LLM Wiki 里的修改是否进入了 RAGFlow。
- 被删除或驳回的知识是否已经从 RAGFlow 撤回。
- 用户再次咨询时，答案是否真的发生变化。
- 当前失败是审核未过、同步失败、检索未命中，还是前端仍命中旧答案。

## 产品目标

让知识运营和客服主管能用业务语言理解每条知识的当前阶段，并能看到它是否已经影响用户咨询结果。

目标状态：

```text
知识在 LLM Wiki 发生变化
  -> 系统识别变化
  -> 系统判断是否允许同步
  -> 系统更新 RAGFlow
  -> 系统用咨询问题验证答案变化
  -> 运营看到生效状态和失败原因
```

## 角色影响

### 顾客

顾客不直接操作该流程。顾客影响是间接的：当已审知识同步并验证生效后，顾客咨询应获得更新后的答案；当知识被删除、驳回或降级后，顾客不应继续收到旧答案。

### 客服 / Operator

客服在转人工场景中提供人工回答，这些回答可能生成待审问答。客服需要知道自己的人工经验是否已经进入知识治理，但不负责同步 RAGFlow。

### 知识运营 / Knowledge Admin

知识运营是核心用户。需要完成：

- 在 LLM Wiki 中审核、修改、删除或驳回问答。
- 查看每条知识是否已同步 RAGFlow。
- 查看该知识是否已影响用户咨询答案。
- 识别失败原因并决定重试、修正或撤回。

### 后台管理员 / System Admin

后台管理员需要看到集成健康、同步失败、RAGFlow 更新失败和咨询验证失败，必要时能暂停同步或重试。

### 微信平台管理员

本需求不直接修改微信平台配置。真实微信接入完成后，咨询验证可以扩展到 live channel，但当前 MVP 以主仓咨询接口验证为准。

## 用户可见阶段

界面和报告应优先使用以下名称：

```text
待审问答
已审问答
同步中
已同步
已生效
撤回中
已撤回
失败
```

避免把主要状态显示为 `candidate`、`artifact`、`sync_job`、`hash`、`vector`。

## 核心场景

### 场景 1：新增已审问答后生效

1. 运营在 LLM Wiki 中新增或批准一条问答。
2. 系统识别该问答满足门禁：已审核、评估通过、有来源。
3. 系统同步到 RAGFlow。
4. 系统用该问题或验收问法发起咨询验证。
5. 咨询答案命中新知识。
6. 运营看到状态：`已生效`。

验收标准：

- 未满足门禁时不能进入 RAGFlow。
- 同步成功但咨询未命中时，状态不能显示为 `已生效`。
- 生效记录必须包含验证问题、返回答案、来源和时间。

### 场景 2：修改已同步问答后替换旧答案

1. 运营在 LLM Wiki 中修改一条已同步问答。
2. 系统识别内容变化。
3. 系统替换 RAGFlow 中对应文档。
4. 系统验证用户咨询返回新答案。
5. 旧答案不再被检索返回。

验收标准：

- 修改不能只新增 RAGFlow 文档，导致新旧答案同时存在。
- 如果旧文档无法删除或停用，状态必须是 `失败` 或 `撤回中`，不能显示为 `已生效`。

### 场景 3：删除或驳回后撤回答案

1. 运营删除 LLM Wiki 问答，或把审核状态改为驳回。
2. 系统识别该知识不再允许作为生产知识。
3. 系统从 RAGFlow 撤回对应文档。
4. 系统验证旧问题不再返回旧答案。
5. 运营看到状态：`已撤回`。

验收标准：

- 删除、驳回、评估失败、来源为空都必须触发撤回策略。
- 撤回失败必须暴露给后台管理员。
- 撤回完成前，不能让运营误以为前端已停止回答旧内容。

### 场景 4：同步失败后可定位原因

1. 知识变更被识别。
2. 系统尝试同步或撤回。
3. 外部服务失败、门禁失败或咨询验证失败。
4. 运营看到失败阶段和可操作建议。

验收标准：

- 失败原因至少能区分：门禁未过、RAGFlow 不可用、替换失败、撤回失败、咨询验证未命中。
- 失败状态不得覆盖旧的事实记录。
- 允许重试，但重试必须保留历史记录。

### 场景 5：扫描 LLM Wiki 已审问答并发现变化

1. 运营点击“扫描 LLM Wiki 已审问答”。
2. 系统读取 LLM Wiki 已审问答目录。
3. 系统对比当前文件 path、内容 hash、审核状态、评估状态和来源引用。
4. 系统把结果归类为：新增、修改、删除、驳回/降级、无变化、阻断。
5. 运营看到本次扫描结果和失败原因。

验收标准：

- 新 path 且通过门禁时，扫描结果显示 `新增`。
- 同 path 内容 hash 变化时，扫描结果显示 `修改`。
- 已登记 active 的 path 在已审目录中消失时，扫描结果显示 `删除`。
- 文件仍存在但审核、评估或来源不满足门禁时，扫描结果显示 `驳回/降级`。
- path 和 hash 均未变化时，扫描结果显示 `无变化`，不得重复同步。
- LLM Wiki 不可达、目录不可读、frontmatter 格式错误或外部同步失败时，扫描结果显示 `阻断`，不得覆盖旧的 active 状态。

## 功能需求

### FR1 知识变更识别

系统应识别 LLM Wiki 中已审问答的新增、修改、删除、驳回和降级。

当前 MVP 可以从手动触发扫描开始；后续支持定时扫描或事件驱动。

扫描结果应使用用户可理解名称：

```text
新增
修改
删除
驳回/降级
无变化
阻断
```

### FR2 同步门禁

只有满足以下条件的问答可以进入 RAGFlow：

```text
审核通过
评估通过
来源非空
```

### FR3 RAGFlow 更新

系统应支持新增、替换和撤回三类更新结果。

### FR4 咨询验证

系统应在同步或撤回后验证前端咨询结果是否符合预期。

验证问题来源：

- 问答原问题。
- 运营维护的验收问法。
- 历史真实用户问法。

### FR5 生效状态展示

系统应展示每条知识的用户可理解状态：待审、已审、同步中、已同步、已生效、撤回中、已撤回、失败。

### FR6 历史记录

系统应记录每次知识变更、同步动作、撤回动作和咨询验证结果。

### FR7 扫描记录

系统应记录每次 LLM Wiki 变更扫描，包括：扫描时间、扫描目录、发现数量、每个文件的变化类型、失败原因和后续动作。

## 非功能需求

- 可追溯：每条 RAGFlow 文档必须能追溯到 LLM Wiki 文件路径和来源材料。
- 可解释：运营能看懂失败原因，不需要理解 hash、document id 或内部 job 名称。
- 安全：未审核知识不得进入生产检索。
- 一致性：修改和撤回不能造成新旧答案同时长期命中。
- 可降级：RAGFlow 不可用时，不得把本地 fallback 误写成生产生效。

## 范围外

- 本 PRD 不定义具体扫描器、数据库表或 RAGFlow API 封装。
- 本 PRD 定义扫描产品目标和验收标准，但不限定扫描器的具体实现方式。
- 本 PRD 不要求立即完成真实微信 live channel 验证。
- 本 PRD 不定义 LLM Wiki Desktop 内部 UI 改造。
- 本 PRD 不把本地 `publishedKnowledge` 作为生产知识源。

## 当前实现状态

已具备：

- LLM Wiki 写入。
- LLM Wiki 状态回读。
- approved/pass/sources 同步门禁。
- RAGFlow 上传和同步 job。
- 主仓咨询链路优先使用 RAGFlow retrieval。
- LLM Wiki 文件到 RAGFlow document 的 `knowledgeDocuments` 生效注册表。
- 主仓回答链路过滤 inactive / superseded document。
- 手动同步后的咨询验证记录。
- operator UI 展示回答生效验证和可回答知识状态。
- LLM Wiki 已审问答目录手动扫描。
- 扫描记录和扫描结果 UI。
- `added/modified` 可显式自动同步并验证。
- `deleted/downgraded` 可自动撤回答复生效权。
- 扫描失败或存在阻断项时生成知识告警，并可在 operator UI 确认。

待补齐：

- 定时自动扫描或事件驱动扫描。
- RAGFlow 物理替换和撤回；当前前端不答旧知识由主仓注册表过滤保证。

## 验收标准汇总

- 未审核或评估未通过的知识不会进入 RAGFlow。
- 已审新增知识同步后，咨询验证命中新答案才显示 `已生效`。
- 已同步知识修改后，旧答案不能继续与新答案同时命中。
- 已同步知识删除或驳回后，主仓必须撤回该知识的回答生效权；RAGFlow 物理撤回作为清理优化，不作为前端不答旧知识的唯一前提。
- 撤回后，咨询验证不能再返回旧答案。
- 失败时能区分失败阶段和原因。
- 每条知识都有 LLM Wiki 路径、RAGFlow 文档、咨询验证和最终状态记录。
- 扫描 LLM Wiki 已审目录时，新增、修改、删除、驳回/降级、无变化和阻断都能被区分记录。

## 进入技术设计条件

进入 `technical-design` 前需要确认：

- RAGFlow 是否支持删除、停用或覆盖 document。
- 咨询验证以主仓接口、RAGFlow retrieval 还是真实微信 channel 为准。
- MVP 阶段扫描目录和命名约定，默认从 `wiki/approved-answers/` 开始。
- LLM Wiki API 是否支持列目录；若不支持，是否允许主仓基于 current project 文件系统扫描。
